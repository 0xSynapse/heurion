# 学术 PDF 原版视图与评注对齐

> 状态：2026-11-09 第 1–4 阶段已实现（见文末「实现进度」），§10 的待确认事项按默认做法实现、仍待确认。相关：`docs/design/IMPORT_EVAL.md`（导入保真评测）、`docs/PLATFORM.md` §5.1 / §5.4（锚点与评论闭环）。

## 1. 背景与目标

现在导入 PDF 是**转换**：Docling 识别版面 → 平台文档模型（标题、段落、表格、图）。转换稿可以编辑、可以给 AI 改，深度审稿、论断核查、评论都基于它。2026-11-08 的修复后，标题、图注、续表、段落接续大体正确（见 IMPORT_EVAL.md），但转换稿终究不是原文：

- 版式、字体、公式、复杂表格的排布丢失，审稿人习惯对着期刊排版读；
- 转换错误（漏图、表格错位、上标丢失）用户很难察觉，会以为是稿子本身的问题；
- 跟作者、编辑沟通时说的是「第 5 页表 2」，转换稿里没有页码。

**目标**：PDF 导入的稿件增加「原版」视图，按 PDF 原样逐页显示；在原版上可以看到并新建评论，深度审稿与论断核查的标注也画在原版的对应位置上。

**不做**：
- 原版视图里**不能改文字**（只读）。修改仍在转换稿里做，经操作层（`apps/platform/src/ops/`）写入；不新增任何写文档的入口，也不回写 PDF。
- 不导出带批注的 PDF（以后再议，见 §9）。
- Word 稿不在本期范围（可以以后用 LibreOffice 转 PDF 后套用同一视图）。

## 2. 核心思路

**评论仍然只有一种锚点**：转换稿里的 `comment(thread)` mark / 块 id（PLATFORM.md §5.1）。原版视图不引入新的锚点类型，只是一个「显示与选区」的映射层：

```
PDF 里的词（页、坐标）  ⇄  转换稿块的文字偏移（node_id, offset）
          ↑ 导入时一次性对齐，存为「原版映射」
```

- **显示**：评论 mark 覆盖的文字 → 偏移 → 映射到 PDF 上的词框 → 在页面上画高亮。
- **新建**：用户在原版上选中文字 → 选中的词 → 偏移 → 调用现有建评论接口（`node_id + snippet + range`），服务端按原规则打锚点。

好处：评论数据、锚点守卫、AI 读评论（`comments_list`）、导出 Word 批注都不用改；两个视图看到的是同一批评论，不会分叉。

## 3. 原版映射

### 3.1 内容

每份 PDF 导入的文档存一份映射（导入时生成，之后不变）：

```jsonc
{
  "version": 1,
  "pages": [{ "w": 595.3, "h": 841.9 }],          // 每页尺寸（pt，左上角为原点）
  "words": [                                       // 全文的词，按页、阅读顺序
    { "p": 1, "b": [72.1, 90.4, 118.6, 101.2], "t": "Background" }
  ],
  "nodes": {                                       // 转换稿块 → 词
    "k3f2": {
      "text": "…导入时块的纯文字…",                 // 用于判断块后来是否被改过
      "spans": [[0, 10, 0], [11, 19, 1]],          // [块内起始偏移, 结束偏移, 词序号]
      "regions": [[1, 72, 88, 523, 160]]           // [页, 左, 上, 右, 下]：块的区域（跨栏 / 跨页时有多个）
    }
  }
}
```

- 词以外的内容（页眉页脚、图内文字、被丢弃的期刊 logo 等）也在 `words` 里，只是不属于任何块：原版上照样能看到、能选，但不能挂评论（见 §5.2）。
- 表格：每个单元格的段落都是一个条目，`regions` 用 Docling 给的单元格框；表格块本身的 `regions` 是整张表（续表合并的有多个页）。
- 图：只有 `regions`（Docling 图框，多面板合并后是合并框），评论整块。
- 大小：一篇 15 页论文约 1.2 万个词，坐标保留 1 位小数，JSON 约 400 KB，gzip 后约 100 KB。

### 3.2 怎么生成

分两边做，避免平台的文字改写（列表识别、续表合并、上标还原、段落接续）把偏移搞乱：

1. **doc-parser**（`apps/doc-parser`）：
   - 用 pypdfium2（已在用，裁图就靠它）抽出每页的字和字框，按空白合成词，输出 `words` 与 `pages`；
   - 每个块额外输出 `regions`：现在 `_postprocess` 末尾删掉的 `_box` 保留下来改名输出；段落接续（`_join_paragraphs`）、图注挂接、面板合并时把区域**累加**而不是丢弃；表格加上单元格框。
2. **平台**（`convert/doc-parser.ts` 之后）：转换稿建好、块 id 分配完后，逐块对齐——
   - 取块的最终纯文字（与 `paragraphText` 同一规则：硬换行记作换行，引用等原子不计文字）；
   - 取块 `regions` 内的词，按阅读顺序拼起来；
   - 两边都规范化（NFKC 处理连字 ﬁ/ﬂ、去掉行末连字符、去空白、小写）后做序列对齐：先整段顺序匹配，失配处用差异算法补齐。对不上的字（OCR 错、Docling 改过的字）不映射，显示时就近取相邻词。

对齐写在平台而不是 doc-parser 里，是因为最终文字由平台决定；doc-parser 只负责给「原料」（词与区域），以后换解析器也只需要提供同样的原料。

### 3.3 质量指标

导入评测（`eval-import.ts`）加一项**原版对齐率**：19 篇论文里，转换稿正文字符能映射到 PDF 词的比例；外加抽样核对映射到的位置是否正确（块的词框落在块区域内）。目标：对齐率 ≥ 98%，基线入库，按容差防退步。

### 3.4 存储与接口

- 存储：`doc_packages` 已经存了 PDF 原文件（`kind='pdf'`, `import_engine`），新增一列 `source_map`（gzip 后的 JSON）。只有 Docling 导入的稿件有映射。
- 接口（权限与读文档相同）：
  - `GET /api/docs/:id/original.pdf`：原文件；
  - `GET /api/docs/:id/source-map`：映射（带 ETag，长缓存，不随文档修订变化）。
- 复制文档（`model/duplicate.ts`）时一并复制，块 id 不变所以映射仍可用。

## 4. 渲染

**用 pdf.js（`pdfjs-dist`）在浏览器渲染**，只画页面（canvas），不用它的文字层：选区与高亮用我们自己的词层（§5），保证选中的东西和映射是同一份数据。

| 方案 | 优点 | 缺点 |
|---|---|---|
| **pdf.js 浏览器渲染（推荐）** | 任意缩放都清晰；不占服务器；公式、矢量图原样 | 前端多约 1.5 MB（按需加载，只在打开原版视图时下载）；PDF 解析在浏览器里，有安全面（见下） |
| 服务端预渲染成图片（pypdfium2） | 前端无新依赖 | 放大发糊；每篇存几 MB 图片；渲染依赖 doc-parser 在线 |

安全与部署：
- 锁定精确版本，且不低于 4.2.67（修复了 CVE-2024-4367 字体脚本执行）；`isEvalSupported: false`，不加载远程字体与外链；
- worker 与 cMap、标准字体文件随前端构建自托管，不走 CDN（与数据外发边界一致）；
- 只渲染可视区域附近的页（虚拟滚动），长文档不卡。

扫描页：PDF 里没有文字层，词来自 Docling 的 OCR 结果（带框），一样能选、能挂评论，但会提示「扫描页文字由 OCR 识别」。

## 5. 交互

### 5.1 视图切换

- PDF 导入的文档，编辑区顶部加「原版 / 转换稿」切换；**默认打开哪个待定**（建议默认原版，见 §10）。
- 评论栏两个视图共用：点评论 → 当前视图滚动到对应位置；切换视图时尽量停在同一块。
- 转换稿里块的右键菜单加「在原版中查看」，原版里任意位置加「在转换稿中查看」，方便核对转换是否正确。

### 5.2 新建评论

- 在原版上拖选文字，弹出与转换稿相同的评论按钮（评论 / 评论并让 AI 处理 / 核查证据）。
- 选区 → 选中的词 → 所属块与块内偏移 → 前端换算成段落内位置，调用现有建评论接口；服务端照原规则打锚点、返回 400 时照原样提示。
- 规则与转换稿一致（PLATFORM.md §5.1）：只能选在一个段落内。原版里一个段落常常跨栏、跨页，这种选区是允许的（同一块）；跨两个段落则提示「评论只能选在一个段落内」。
- 选到页眉、图内文字等不属于正文的内容：提示「这部分没有导入正文，不能挂评论；可以评论整张图 / 整页附近的段落」。
- 点图、表的空白处：评论整块。

### 5.3 显示

- 评论高亮：mark 覆盖的偏移 → 词框，按行合并成矩形画在页面上；整块评论画块区域的边框。关闭的线程不画（与转换稿一致）。
- 深度审稿与论断核查：它们的结果本来就是带锚点的评论 / 核查记录，按同样方式画，颜色与转换稿一致。
- 转换稿里**已修改过**的块：映射是导入时的文字。当前文字与 `nodes[id].text` 不同时，用首尾相同部分对齐（平台是最小差异写入，大部分字不动）；评论落在改动区域里时退回画整块区域，并在评论卡片上标「转换稿里这段已修改」。
- AI 修改建议、待采纳修订只在转换稿里显示；原版对应块旁边画一个小标记，点击跳到转换稿。

### 5.4 页码

有了映射，评论和审稿结果都能带上页码：评论卡片显示「第 5 页」；`comments_list` 给 AI 的锚点信息里加 `page`，AI 回复时可以说「第 5 页表 2」。这是只读信息，不影响锚点规则。

## 6. 对现有规则的影响

| 规则 | 影响 |
|---|---|
| AI 只能经操作层写文档 | 无。原版只读；建评论走现有评论接口 |
| 锚点颗粒度、锚点守卫 | 无。原版选区换算后用同一接口、同一校验 |
| 正式引用只能来自 `insert_citation` | 无 |
| 数据外发边界（cordis.yml） | 无。pdf.js 及其资源自托管 |
| 导出 Word | 无（评论照旧写成 Word 批注） |

## 7. 不支持 / 降级的情况

- **poppler 兜底导入**：没有块区域，不生成映射。仍可打开原版视图看 PDF，但不画评论、不能在原版上建评论，顶部提示原因。
- **转换稿里新增的块**（导入后 AI 或用户新写的）：原版里没有对应位置，评论只在转换稿显示，评论卡片标「原版中没有这段」。
- **转换丢掉的内容**（Docling 没识别的图、被当成页眉丢掉的句子）：原版上能看到但不能评论，正好帮用户发现转换遗漏；评论只能挂到附近段落。
- **旧文档**（本功能上线前导入）：没有映射。可以提供「重新生成原版映射」（重跑 doc-parser 只取词与区域，再按块文字对齐；块已改动的按 §5.3 降级）。

## 8. 实施步骤

| 阶段 | 内容 | 验收 |
|---|---|---|
| 1 原料 | doc-parser 输出 `words` / `pages` / 每块 `regions`（含段落接续、图注挂接、面板合并、表格单元格的区域累加）；测试 | doc-parser 测试；19 篇实跑区域非空率 |
| 2 对齐 | 平台对齐算法、`source_map` 存储与两个接口；导入评测加原版对齐率 | 对齐率 ≥ 98% 入基线；单元测试覆盖连字、行末连字符、上标、跨页段落 |
| 3 只读视图 | pdf.js 渲染、视图切换、评论 / 审稿高亮、评论定位、页码 | e2e：导入 → 深度审稿 → 原版上看到高亮并能跳转 |
| 4 原版建评论 | 词层选区、换算、建评论、提示文案 | e2e：原版选中 → 建评论 → 转换稿里同一处出现 mark；跨段落被拦 |
| 5 收尾 | 已修改块的降级、旧文档补生成、复制文档、`comments_list` 带页码 | 文档更新（PLATFORM.md、IMPORT_EVAL.md） |

每个阶段单独可用：做完 3 就能「对着原版看审稿结果」，4 是在原版上直接写评论。

## 10. 待确认

1. **原版只读**：修改只在转换稿里做（本文按此设计）。
2. **默认视图**：PDF 导入的稿件打开时默认显示原版还是转换稿？建议默认原版，审稿场景更自然。
3. **范围**：本期只做 Docling 导入的 PDF；poppler 兜底与旧文档只给只读查看。

## 11. 实现进度（2026-11-09）

已实现：

| 阶段 | 实现 |
|---|---|
| 1 原料 | doc-parser 输出 `source`（各页尺寸、全文的词）与每块的 `src`（区域、块文字 → 词的对齐，表格另有单元格对齐）。区域取 Docling 给的全部位置（跨页段落有多处），接段落时累加 |
| 2 对齐与存储 | 平台 `bindSourceMap` 换成按块 id 记，存在 `doc_packages.source_map`（gzip）；`GET /api/docs/:id/original.pdf`、`GET /api/docs/:id/source-map`；复制文档时一并复制 |
| 3 只读视图 | 顶栏「原版 PDF / 转换稿」切换；pdf.js 按需加载、只画进入可视区附近的页；评论与审稿批注画成文字高亮或整块虚线框，点高亮打开对应评论，点评论卡片滚到原版位置 |
| 4 原版建评论 | 词层原生选区 → 所属块与块内文字 → 现有建评论接口（块在转换稿里没改过时带段落内位置，否则只带文字由服务端查找）；跨段落、选到没导入正文的字时给提示 |

与设计不同的地方：

- **对齐在 doc-parser 里做**（设计 §3.2 写的是平台）：同一份文字层对齐还要用来修 Docling 的文字（补短横、上下标、段首小标题，见 `apps/doc-parser/README.md`），doc-parser 本来就知道每块的最终文字。平台只做两件事：段落去首尾空白后平移下标、续表合并时单元格行号下移，然后换成块 id。
- 词层直接用映射里的词，不用 pdf.js 的文字层（与设计一致），对齐覆盖率在 5 篇论文上实测 99.8%–100%（非空白字符）。
- 竖排印刷的页：doc-parser 解析前把这些页转正，映射的坐标按转正后的页面，`pages[i].rot` 记下额外转的角度；原版视图按原文件渲染时同样转，横向页按各自宽度缩放。

按默认做法实现、仍待确认（§10）：原版只读；打开文档默认显示转换稿，原版需要点顶栏切换；只做 Docling 导入的稿件，其余只能查看原版。

还没做：

- 评论卡片上的页码、`comments_list` 给 AI 的页码（§5.4）；
- 转换稿里改过的块：现在只在原版上退回画整块，评论卡片上没有「这段已修改」的标记；
- 转换稿里块的「在原版中查看」入口；
- 旧文档补生成映射；
- 导入评测加「原版对齐率」指标（现在是手工测的）；
- pdf.js 的 CMap 与标准字体文件没有随前端打包：期刊 PDF 基本都内嵌字体（测过的中英文论文都正常），没内嵌字体的 PDF 可能显示不全。
