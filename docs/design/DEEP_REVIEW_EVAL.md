# 深度审稿评测集设计（草案）

> 状态：2026-11-09 植入错误已编写（19 篇、57 处，`eval/deep-review/injections/`），见第 10 节；人工判定与模型审稿的基线待跑。配套 [`DEEP_REVIEW_PRODUCT.md`](DEEP_REVIEW_PRODUCT.md)。

## 1. 为什么要重建

- 现有 `paper/benchmarks/run-7papers-review.ts` 的 7 篇论文（8 个已知错误）已经被规则针对过：`claims/extract.ts` 的豁免与检查规则里写死了这些论文的具体数字和句式。它们只能作为开发集，不能用来报告效果。
- 深度审稿的成败在误报，而参考的 PAT 论文（arXiv:2606.28277）也只测了召回、没有测误报。我们必须自己测「干净稿件上报了多少假问题」。
- 实测（2026-11-08）：一篇无错误的中文稿件被报 3 条，全是误报，其中 2 条为「致命」。

## 2. 指标

| 指标 | 定义 | 用途 |
|---|---|---|
| 干净稿件误报数 | 每篇干净稿件上被判为误报的 critical + major 条数（均值与分布） | **主指标**，决定能否上线 |
| 精确率 | 判为真问题的条数 / 报出总条数，按严重度分别统计 | 用户信任度 |
| 召回率 | 被检出的标注错误数 / 标注错误总数，按错误类型分别统计 | 能力覆盖 |
| 严重度准确率 | 真问题中严重度与标注一致的比例 | 排序是否可信 |
| 定位准确率 | 真问题的批注锚点落在标注原句上的比例 | 用户能否找到 |
| 单篇成本与耗时 | 输入 / 输出 token、模型调用次数、总耗时 | 定价 |
| 稳定性 | 同一篇跑两次，报出问题集合的重合度 | 温度 0 也有波动，需要知道幅度 |

上线门槛（建议，待评测跑出基线后再定）：干净稿件平均误报 ≤ 0.5 条（critical + major），critical 精确率 ≥ 90%。

## 3. 样本类型

1. **干净稿件**：已发表的开放获取论文，假定没有重大错误。审稿报出的每一条都要人工判定真假（已发表论文也可能真有错，判为真问题时记为「意外发现」，不算误报）。
2. **植入错误稿件**：在干净稿件的副本里人工植入 2–3 处客观错误，记录原文、改后文字与位置。用同一批论文做干净版和植入版，干净版的判定结果可以复用，标注量减半。
3. **真实勘误稿件**：已发表正式勘误、且勘误声明写明原文错在哪里的论文。**前提是 PMC 中的原文没有被改正版覆盖**，很多出版商发勘误后会直接替换原文，必须逐篇核实后才收。数量少但最接近真实分布。

## 4. 错误类型（只限客观错误，不评主观写作质量）

| 编号 | 类型 | 植入示例 |
|---|---|---|
| E1 | 样本量前后不一致 | 摘要写 412 例，结果写 421 例 |
| E2 | 百分比或分母算术错误 | 98/206 写成 (52.6%) |
| E3 | 摘要与正文结果数值不一致 | 摘要 HR 0.72，结果 HR 0.78 |
| E4 | 置信区间与点估计不自洽 | 点估计落在区间外，或上下界倒挂 |
| E5 | 统计方法与结果报告不一致 | 方法只写 t 检验，结果报 Mann-Whitney |
| E6 | 结论夸大 | P=0.21 写成「显著改善」；观察性研究写「导致」 |
| E7 | 表格内部算术错误 | 分组人数加总不等于总数，单元格百分比算错 |
| E8 | 引用歪曲 | 引文原文 25% 写成 35%，或方向写反（文献核查接入后启用） |
| E9 | 外部论断缺引用 | 引言里的流行病学数字删掉引用（文献核查接入后启用） |

植入时**不能只用一种固定句式**：每类错误都要有中英文、不同措辞、在正文段落与表格中各自出现的变体，避免再次出现「规则只认评测稿件写法」的问题。

## 5. 数据切分

- **开发集**：可以随意看结果、调规则和提示词。包含原 7 篇（标记为「已被规则针对过」）与新语料的一部分。
- **测试集**：封存。调试期间不看单篇结果，只在里程碑时跑一次、只看汇总指标，并记录代码版本。约占新语料的 40%。
- 同一篇论文的干净版与植入版必须在同一个切分里。

## 6. 文件与格式

仓库内（进 git）：

```
apps/platform/eval/deep-review/
  manifest.json          # 论文清单：来源、许可、切分、语言、学科、研究类型
  injections/<id>.json   # 植入错误：原文、改后文字、位置、类型、严重度
  labels/<id>.jsonl      # 标准答案：植入错误 + 勘误错误 + 人工确认的意外发现
  adjudications/<run>.jsonl  # 每次评测报出问题的人工判定
```

仓库外（`data/eval/deep-review/`，不进 git）：原始全文 XML、转换后的稿件、每次运行的原始输出。沿用现有 `eval:fetch` 的许可核对，只收 CC-BY / CC0。

标准答案一条：

```json
{
  "label_id": "PMC12644478-E3-1",
  "paper_id": "PMC12644478",
  "variant": "injected",
  "source": "injection",
  "type": "E3",
  "severity": "critical",
  "quote": "The adjusted hazard ratio was 0.78 (95% CI 0.61–0.98)",
  "section": "Results",
  "description": "摘要报告 HR 0.72，结果段改为 0.78",
  "related_quotes": ["hazard ratio 0.72 (95% CI 0.58–0.89)"]
}
```

人工判定一条：

```json
{
  "run_id": "2026-11-xx-<git sha>",
  "paper_id": "PMC12644478",
  "variant": "clean",
  "finding_key": "<问题类型 + 原句归一化后的哈希>",
  "verdict": "false_positive",
  "matched_label": null,
  "severity_ok": null,
  "anchor_ok": true,
  "annotator": "A",
  "note": "表头已声明 n (%)，单元格不带 % 是规范写法"
}
```

`verdict` 取值：`true_positive`（命中标准答案）、`unexpected_true`（标准答案外的真问题，确认后补进 labels）、`false_positive`、`duplicate`（同一问题重复报）、`unclear`。

## 7. 评测流程

1. `eval:fetch` 下载全文并核对许可 → 转成平台文档（JATS XML → 带标题、段落、表格、引用的稿件）。
2. 按 `injections/` 生成植入版。
3. 每篇（干净版、植入版）各跑两次深度审稿，记录全部报出问题、token、耗时与代码版本。
4. 自动匹配：报出问题的锚点原句与标准答案原句重叠、且类型相容，记为候选命中。
5. 人工判定：自动匹配结果由人确认；未命中的每一条判定真假。可先用模型做预判，但最终以人工为准。干净版判定过的问题，在植入版中原样出现时直接复用。
6. 汇总第 2 节指标，结果写入 `eval/deep-review/report.md`，附代码版本。

## 9. 待决定

1. **中文稿件来源**：产品首先面向中文用户，但开放获取的中文论文少、许可不清。候选：课题组自有稿件（需作者书面同意，只在内部评测使用）、中文开放获取期刊中明确为 CC-BY 的论文。
2. **人工判定由谁做**：干净稿件上的误报判定需要懂临床研究方法学的人，建议至少两人独立判定一部分样本，以衡量判定一致性。
3. **规模**：第一批建议 20 篇（干净版 + 植入版 = 40 份稿件），每份跑两次，约 80 次深度审稿。

## 10. 进展（2026-11-09）

- **植入错误**：第 8 节的 19 篇（开发 11、测试 8）每篇 3 处、类型互不相同，共 57 处（E1 10、E2 6、E3 8、E4 8、E5 8、E6 9、E7 8；
  致命 14、重要 29、次要 14）。逐条校验：原文在稿件里恰好出现一次、植入后对照原文仍在、同篇类型不重复。E8 / E9 未植入（文献核查接入后再加）。
- **原文自带的不一致**：编写时通读发现的发表版原文问题记在 `eval/deep-review/known-issues.md`，审稿报出这些判为「意外发现」。
- **只跑规则检查**（开发集，`--no-llm`）：33 处植入只检出 1 处（E2）。规则只覆盖少数固定句式，召回主要靠模型审稿。
- **模型审稿改动**（`claims/service.ts`、`claims/review-evidence.ts`，与基线对比待跑）：每条意见要逐字引用原句与证据（另一处矛盾的原文），
  程序核实两段引文都在稿件里，对不上或没有证据的不报；提示词只要客观错误、写明严重度定义、不报主观意见；每章节最多 3 条；
  跨章节按引文数字组合去重。动机：主评测集 19 篇实测（未改前）模型每篇报 20–50 条（684 条），数量明显偏多；
  这些意见的真假还没判定过，改动是否减少了误报、有没有伤到召回，要靠下面的对比来回答。
- **实测对比**（开发集 11 篇 × 干净 / 植入，`deepseek-flash`，各跑一次；召回按植入标准答案自动匹配；误报为模型预判，未经人工判定）：

  | 版本 | 植入检出（33） | 干净稿件致命 + 重要 | 其中模型预判误报 | 每份输入 / 输出 token | 每份耗时 |
  |---|---|---|---|---|---|
  | 改动前 | 18 | 259 | 约 74%（抽 39 条） | 2.5 万 / 10 万 | 53 s |
  | 证据核实 + 新提示词 + 每章节 ≤ 3 条 + 跨章节去重 | 21 | 49 | 15 | 2.9 万 / 4 万 | 41 s |
  | + 各章节附摘要作对照 | 25 | 98 | 28 | 3.6 万 / 4.5 万 | 40 s |
  | + 不报「没报告」类 + 全文复核 | 23 | 69 | 17 * | 5.7 万 / 5.1 万 | 79 s |

  \* 预判与全文复核用同一个模型，复核去掉的正是它认为不成立的，这一列的误报数偏乐观。
  - 改动前每份约 45 条意见，自动匹配只要原句里出现被改的数字就算命中，召回因「撒网」偏高。
  - 摘要对照：「摘要与正文不一致」（E3）从 1 / 5 提到 5 / 5。
  - 全文复核：检出 25 → 23（单次运行的波动与误删分不开），耗时翻倍。
  - 剩下的误报多是章节审稿看不到别处内容，把写在方法或表格里的东西当成「没报告」「对不上」。
- **去重核查后的两处修正**（在上表之后，尚未重跑）：回放去重前后差得最多的 3 篇干净稿件（53 → 5、71 → 6、31 → 3），被合并掉的八成多是
  规则检查「表格格子漏标百分号」——「n (%)」格子算得对、只是没写 % 号也报，一张表几十条，全是误报；另外去重规定「同一块上有规则意见，模型意见一律让位」，
  把模型查出的别的真问题（如「黄斑病变 2 (20)，N = 20 应为 10%」）也吞了。修正：单独漏标百分号不报，只报算不对的；
  表格不同的格分别报；模型意见只在与规则意见针对同一个单元格值时才让位。按数字组合跨章节合并只发生 1 次，且确为同一问题。
- **下一步**：从「+ 摘要对照」与「+ 全文复核」两版干净稿件的意见里各抽 20 条做人工判定，确认模型预判是否可信、全文复核去掉的是否确为误报，再定全文复核是否默认开启。
  模型预判脚本目前在临时目录（scratch/prejudge.ts），人工判定流程定下后再正式入库。
